# task-logs

Task logs, their endpoint and proxy.

Generated by `make records` from the decisions whose `topic` (or `also`) is this one; edit the decisions, not this page.

## Current

### Reading logs

- **The live log tail reads the worker range endpoint** (D23): The server reads new log bytes from
  the worker’s range endpoint using `from`. Since D175 the browser requests each part while the
  attempt runs.

### Logs

- **Logs: stdout and stderr only; one structured line format for every task kind; big logs as links;
  an extension's own events on its page** (D514, planned (M5.2i5)): A task logs through stdout and
  stderr only, a plugin too: no log messages in the protocol (order, masking, the log file and
  server, a crashed plugin's log kept, any language). One structured line format, ours, recognised
  on either stream for every task kind: a JSON line (`schedr_log`, `level`, `message`, `fields`,
  `time`) shown in the Logs tab with its level and fields and filterable by level; any other line
  stays plain. Written by the helpers (Python `logging` handler and the plugin channel's logger, the
  Rust crate, `schedr task-ctx log`); the Python runner installs the handler on the root logger
  itself, so a Python task's `logging` is structured with no change to its code (a task configuring
  logging itself keeps its own). No stdout/stderr split stored: a structured line already tells the
  plugin's own from the work's. A log too big to copy stays where it is, behind a decision 513 link;
  no plugin serving remote logs. An extension's own events (discovered, skipped and why, refused)
  are reported by the worker and shown on the extension's page.
