# The web UI

`schedr ui` serves the pages over one or more deployments' webservers. A deployment is one
schedr: its master, workers, webserver and database. The UI talks only to those webservers'
REST APIs. It never opens a database, and it never calls a worker.

`schedr standalone` serves the same pages at `/` on the REST API's port. That UI has one
deployment, named `default`, which is the name in a page's address. Standalone ignores
`[ui] deployments`.

The pages take actions. Trigger and Pause or Unpause are on a DAG's page. Cancel is on a
queued or running run's page, and on a task that has not ended, in its panel. Retry is on
an unschedulable task. Drain and Resume are on the [Workers](#workers) page. Each button
opens a dialog that says what will happen. Confirming sends the command, and the result
shows at the top of the page (see [Actions](#actions)). The lists, a DAG's page, a run's
page and the workers page update while they are open (see [Live updates](#live-updates)).

## Actions

A button opens a dialog of the UI's own. The dialog says what will happen. Confirm sends
the command. Cancel closes the dialog and sends nothing. A second click on Confirm, while
the first request is on its way, is ignored.

The result is added at the top of the page, above the part that updates itself, so a later
update leaves it there. It reads the command every second until the master has decided:

- **pending.** "sent; waiting for the master to decide."
- **applied.** "applied." A trigger that was applied links to its new run.
- **rejected.** "rejected," with the master's reason.

A command that was sent, and then can't be read, stays pending. It says it can't be read
now, and why, and that it is trying again. It keeps being read. It doesn't say the command
was not sent. A command that couldn't be sent says "not sent" and why. That is the
webserver out of reach, the webserver refusing the command, a deployment this UI doesn't
show, a trigger's moment that isn't one of the forms below, or any other failure the
request hit. That result isn't read again.

While a dialog is open, the page does not read its live parts again. A reload would replace
the dialog. When the dialog closes, the page reads those parts once.

An action is taken only from the UI's own pages. Anything else is refused (see
[Network and security](08-network.md#another-site-acting-through-a-visitor-s-browser)).
A command the UI sends is recorded with the name of the person signed in at the UI, when the
webserver can tell the call comes from `schedr ui`; otherwise it is `anonymous`. How people
sign in, and how the UI proves itself, are in
[Network and security: Sign-in](08-network.md#sign-in).

**Trigger**, on a DAG's page, starts a manual run. The dialog takes the moment the run is
for, in the forms `schedr runs trigger --for` takes: a date-time with its offset
(`2026-10-15T03:00:00+02:00`), one without (read as UTC), or a date (midnight UTC). Empty
means now. As the moment is typed, the dialog shows it in UTC and in the browser's zone,
the same way the pages show other times. A moment with no offset adds "no offset given:
read as UTC". One that isn't one of those forms is shown as an error. Confirm doesn't send
it, and the result says it was not sent, and why.

**Pause**, on a DAG's page while the DAG is active, tells the scheduler to create no more
of its runs until it is unpaused. The dialog offers "Also cancel its queued and running
runs". Leaving that unchecked pauses only. **Unpause** is shown instead while the DAG is
paused, and the scheduler creates its runs again. The button follows the DAG's state as the
page updates: once a pause is applied, the page shows Unpause.

**Cancel run**, on a run's page while the run is `queued` or `running`, stops its running
tasks and cancels the rest. A task that has already ended keeps its result.

**Cancel task**, in the task's panel while the task has not ended, stops it if it runs and
cancels it at once if it has not started. The tasks downstream of it are cancelled. A task
has ended when its state is `success`, `failed`, `cancelled`, `skipped` or
`upstream_failed`. **Retry** is in the panel while the task is `unschedulable`: every
worker that could run it rejected it, and it is queued again, for every worker. An
unschedulable task offers both.

**Drain** and **Resume** are on a worker's row (see [Workers](#workers)).

## Live updates

The DAG list, a DAG's page, the runs list, a run's page and the workers page update
themselves. An open task panel updates with its run, except on the Logs tab, where the log
is followed on its own.

The webserver follows the database's writes and serves what changed at `GET /api/v1/events`
(see [Network and security](08-network.md#the-events-stream)). A `run` or `dag` event names
that run or DAG. A `workers` event says the workers changed. None of them carries the new
state, and `refresh` means anything may have changed. The UI keeps one of these streams per
deployment and tells each open page when something that page shows may have changed. The
page then reads the new state. If the stream ends or can't be opened, the UI opens it again
after 1 s, then waits twice as long each time, up to 30 s. When the stream is back, the open
pages read themselves again, since anything may have changed while it was down.

Each open page holds its own stream to the UI. The page hears about a deployment at most
once a second. A change that arrives during that second is sent when the second is up, so
the last one is not dropped, and the page reads its live parts again. A quiet stream sends a
ping every 15 s. Once nothing has arrived for 30 s, not even a ping, the page reads those
parts every 5 s. That covers a proxy which buffers the stream and holds the pings back (see
[The events stream](08-network.md#the-events-stream)). While an action's dialog is open, the
page leaves its live parts as they are. When the dialog closes, it reads them once (see
[Actions](#actions)).

| Page | What is read again |
|---|---|
| The DAG list | The list, when a DAG is defined, changed, paused or removed. A new run leaves the list as it is. |
| A DAG | Its facts and its 50 newest runs, when that DAG changes or one of its runs does. |
| The runs list | The runs on this page, with the same filters and the same place in the list, when a run changes. |
| A run | The summary, the graph, the tasks and the commands, together, when that run, a task or an attempt changes. The open panel is read on its own and stays on the same task and tab. The Logs tab is left as it is. |
| The workers page | The list, when a worker registers, changes state, or is seen. A heartbeat counts as seen. |

The writes announce what changed, through triggers in the database. The triggers are on by
default. Stress scenarios 15 and 15b measured them at about 2-3% of the master's throughput,
within the noise between runs (see [Stress tests](11-stress.md)). `[database]
change_notifications = false` turns them off.

`schedr db migrate` applies the setting, and so does `--migrate` (`schedr master --migrate`
and `schedr standalone --migrate`), once that process holds the master's lease, including when
the schema is already up to date. A running master never applies the setting on its own.
Restarting it picks the setting up only with `--migrate`. The webserver follows the triggers'
state in the database. That state is written only when it differs from the setting. On
Postgres the triggers are turned on or off with `ALTER TABLE`, a brief exclusive lock on each
of five tables: runs, task instances, attempts, DAGs and workers. On SQLite the triggers stay
and read a one-row switch, `changes_switch`.

On Postgres, with the triggers on, the webserver is notified when the writing transaction
commits: one notification per run that transaction changed, one per DAG, and one if the
workers changed. On SQLite there are no notifications. The writes append a row to a
`changes` table, which keeps about the last 1,000 rows, and the webserver reads the new rows
every second while the triggers are on. If a change was missed, the pages refresh once and
following continues.

The webserver reads whether the triggers are on before it follows, and again every minute
while it follows. Turned off meanwhile, it sends `refresh` and switches over to the timer.
When the changes aren't followed, it sends `refresh` every `[webserver] refresh_interval`
(15 s by default, at least 1 s: a shorter value is treated as 1 s). That is the triggers
off, or no listening connection: `[database] notifications = false`, or a pooler in
transaction mode unless `[database] notifications_url` points straight at Postgres. It uses
the same check as the master's commands (see [The master](04-master.md)). While it is on the
timer because the triggers are off, it reads them again at each refresh. Turned on
meanwhile, it follows from then on. With the triggers off it logs that the database doesn't
announce its changes and names the interval.

A running try's log grows in the Logs tab of [the task panel](#the-task-panel).

## The DAG list

`/` lists every deployment's DAGs, sorted by DAG id and then by deployment name. The columns
are the DAG, its state (`paused` or `active`), its schedule, its tags, and where it is
defined: the root and the path, as the CLI writes them (`etl:team_a/sync.py`). A DAG that other files also define is marked `conflict`
(see [Parsing and code versions](06-parsing.md)).

When the UI has more than one deployment, a Deployment column names which one each DAG
belongs to. With one, as in standalone, that column is absent. A DAG's address is
`/d/<deployment>/dags/<dag id>`.

The UI asks every deployment at the same time. One that can't be reached, or that answers
with an error, is named in a warning (`Unavailable: <name>: …`), and the DAGs of the others
are still listed. A connection that doesn't complete gives up after 5 s, and a request that
doesn't finish gives up after 30 s. The page is sent when the last deployment has answered
or given up. `schedr ui` sends no credentials. A webserver that requires a token answers
with an error, and that deployment shows up as unavailable. The chart's default policy
allows anything from the same namespace without a token (see
[Deployment](10-deployment.md#inside-an-istio-mesh)). The list updates when a DAG changes
(see [Live updates](#live-updates)). A later update asks again for a deployment that was
unavailable.

## A DAG

A DAG's page shows its state (`paused` or `active`), its description, its schedule, where it
is defined, and its tags. **Trigger** is always there. **Pause** is there while the DAG is
active, and **Unpause** while it is paused (see [Actions](#actions)). The schedule is
written as `schedr dags list` writes it (`0 3 * * * (Europe/Warsaw)`, `every 1h`, a dash
when there is none). The zone in parentheses is the schedule's own zone. When other files
define the same id, a warning lists them and says that none of them runs until one is left.

Below that are the 50 newest runs, newest by the moment they are for: the run id, its state,
that moment, its kind, when it was triggered, by whom, and when it ended. The ended time is
blank while the run is going. Each run links to [its page](#a-run). "all runs of this DAG"
opens the [runs list](#the-runs-list) for this deployment and this DAG, newest triggered
first.

Opening a DAG asks that one deployment. If it doesn't answer, the page says the deployment
is unavailable. An unknown deployment, an unknown DAG or any other path is a not-found page,
with a link back to the list. The page updates when this DAG changes or when one of its runs
does (see [Live updates](#live-updates)).

## The runs list

The header's Runs opens `/runs`: the runs of every deployment, in one list. The newest
triggered run is first. Runs triggered at the same moment are ordered by run id, the greater
id first. A scheduler round triggers its runs at one moment, so **Older runs** is counted
from the last run on the page, its trigger time and its id, and the rest of that moment
stays in order.

The columns are the run, its DAG, its state, the moment it is for, its kind, when it was
triggered, by whom, and when it ended. The ended time is blank while the run is going. Each
run links to `/d/<deployment>/runs/<run id>`. With more than one deployment, a Deployment
column names which one, and a deployment filter is offered. Choosing one asks only that
deployment. With one, as in standalone, the column and the filter are absent.

The other filters are a DAG id and a state (`queued`, `running`, `success`, `failed` or
`cancelled`). Empty means any. The same filters go to each deployment that is asked. A state
other than those five, or a DAG id that isn't valid, is a bad-request page ("That isn't a
run state.", "That isn't a DAG ID: …"). A valid DAG id with no runs leaves the list empty.
**clear** returns to the whole list.

The page lists 50 runs. A full page offers **Older runs**, which continues from the last run
shown. The page after the last one says "No runs before these." An empty list says "No
runs."

The UI asks the deployments at the same time, as on the DAG list, and gives up after the
same waits: 5 s to connect, 30 s for the request. One that can't be reached, or that answers
with an error, is named in a warning (`Unavailable: <name>: …`). Its runs are missing from
that page and from the older ones reached from it. Those pages start after the last run this
page showed, so a run this page missed is not added later. Load this page again once the
deployment answers. A live update asks the deployments again, and one that answers is
included from this page's place in the list. A later page asks again: a deployment that
answers there adds its runs from that point on. The list updates while it is open, filters
and place included (see [Live updates](#live-updates)).

## A run

A run's page is `/d/<deployment>/runs/<run id>`. It shows the run id and its state, then one
line:

- `failed`. When any task's state is `failed`, those tasks are named ("failed: task load
  failed", or "failed: tasks extract, load failed");
- `cancelled`, in the same way, for tasks whose state is `cancelled`;
- `running: 2 of 5 tasks running`. Tasks that are `running` or `cleaning_up` count toward
  the first number. When some are `unschedulable`, the line continues "; can't be
  scheduled: …" with those tasks;
- `queued` or `success` as that word alone.

The facts are the moment it is for, its kind, when it was triggered and by whom, when it
started and when it ended. Started and ended are left out until they have happened. Times
are shown as on the other pages. While the run is `queued` or `running`, **Cancel run** is
offered (see [Actions](#actions)).

The graph is the DAG version this run started with (see
[Parsing and code versions](06-parsing.md)). When its tasks ran on more than one version of
the code, a warning says the code changed during the run and how many versions its tasks
ran on ("The code changed during this run: its tasks ran on 2 versions of it."), and lists
those hashes, in the order the run first used them.

Opening a run asks that one deployment. If it doesn't answer, the page says the deployment
is unavailable. An unknown deployment, or a run id that isn't in it, is a not-found page,
with a link back to the list. While the page is open, the summary, the graph, the tasks and
the commands are read again together when the run changes. The open panel is read on its own
(see [Live updates](#live-updates)).

### The graph

The tasks are laid out in layers, top to bottom: each task is in a layer below the tasks it
waits for. A box is coloured by the task's state. It shows the task name, shortened when the
name is long, then the state, and the outcome when that outcome is something other than
`SUCCESS`. Hovering a box shows the full task id and the state. Until the run has task
instances, the boxes have no state yet, and choosing one says the task isn't in the run.

A solid edge is one where the downstream task takes the upstream task's output. A dashed
edge is order only: it runs after, and receives nothing. The legend says "takes the output"
and "runs after". A pair with both kinds of edge is drawn as one solid edge, because the
data edge already puts them in that order. A DAG version with no tasks says "This DAG has
no tasks."

### The task panel

Clicking a task, in the graph or in the tasks table, opens its panel beside the graph. The
rest of the page stays put. On a narrow window the panel sits under the graph. Until a task is
chosen, the panel says "Choose a task to see its attempts, output and log."

While the task has not ended, the panel offers **Cancel task**. While it is
`unschedulable`, it also offers **Retry** (see [Actions](#actions)).

The panel's address is the run page's with `?task=<task id>`, and `&tab=` for the open tab
(`attempts`, `output`, `logs` or `cleanup`) and `&try=` for one try's log. A link or a
reload keeps the panel as it was. The Attempts tab is open when the address names none, or
names a tab other than those four. The close control returns to the run page. A task id that
isn't in the run is a not-found page. Opened from the page, the panel says the task isn't
there.

While the page is open the panel reads itself again when the run changes, and it stays on
the same task and tab. The Logs tab does not: the log is followed on its own, and the rest
of that tab stays as it was when it opened.

**Attempts** lists the tries, oldest first. A try that has not ended is `running`. The
columns are the try, its status, the worker, how long it ran, its peak memory, and when it
started. Beside the status is how the worker started it, `spawn` or `fork`, once that has
been reported. Duration and peak memory are blank when the worker did not measure them. The
error is on the next line, with its traceback under Traceback. No tries yet says "No
attempts yet."

**Output** shows the outcome, the size of the pretty-printed value, and that value. Only
the last 64 KiB is on the page, and when the value was cut the panel says "Only its end is
shown (the last 64 KiB)." **download** is the whole pretty-printed value. While the task
has no output, the panel says "No output (yet)."

**Logs** shows one try's log. The last try is shown when the address names none, or names a
try the task doesn't have. The panel shows the last 256 KiB. When that is not the whole
log, it says "Only its end is shown (the last 256 KiB)." and the text starts at the first
whole line. A line longer than the tail is shown from the cut. The standard 16 ANSI colours
are shown, along with bold, faint, italic and underline. A 256-colour or RGB code is left
out, and any other escape sequence is removed. The line names the whole log's size, and
says "still running" while the attempt runs. That line stays as it was when the tab opened.

While the try runs, the page reads what is new and adds it: about once a second, and straight
on when a lot is already waiting. The colours carry from one part of that new text to the
next. When the try has ended and the rest of the log is shown, the page stops following. If
following can't read the log, the page adds `The log can't be followed any more: …` and
stops. A worker or the webserver that is out of reach is tried for 30 s first. Any other
failure stops at once.

When the log can't be read on opening, the panel says why: for example the try has not
started or never did, the worker is offline or lost, it can't be reached, or the file is
unavailable at that worker and may have been deleted. A task that has not been tried says
"No log to show: It hasn't been tried yet."

**Cleanup** says "This task has no cleanup." Per-task cleanups come in M4.

### Tasks

The tasks table lists each task of the run: its id, its state (and the outcome, when that
is not `SUCCESS`), how many tries, why it waits or can't be scheduled, and when it last
changed. The reason is blank when there is nothing to say. Clicking the task id opens the
panel. Before the run has task instances, the table says "No tasks yet: the run hasn't
started."

### Resources

Resources says "This run has no resources." The section stays empty until resources exist
(M4).

### Commands

Commands is the history of commands about this run, oldest first: the trigger that created
it, when a command did, a cancel of the run or of one of its tasks, a retry of one of its
tasks, and a pause that cancelled it. A run the scheduler created has no trigger row. Each
row is when it was asked, by whom, the command (`trigger_run`, `cancel_run`, `cancel_task`,
`retry_task` or `pause_dag`) and the decision (`pending`, `applied` or `rejected`), with
the master's reason when it gave one. A command the UI sent carries the name of the person
who took the action, or `anonymous` (see [Sign-in](08-network.md#sign-in)). None yet says
"No commands about this run."

## Workers

The header's Workers opens `/workers`: every deployment's workers, in one list, ordered by
deployment name and then by worker id. The columns are the worker, its state, the queues
it serves, how many attempts are running of its slots (`2 / 4`), its schedr version, and
when it was last seen. Last seen is its last heartbeat, shown as other times are. With
more than one deployment, a Deployment column names which one. With one, as in standalone,
that column is absent.

The state is `active`, `draining`, `disconnected`, `offline` or `lost`. A worker drained
for maintenance is also marked `drained`. Its warning messages are listed on the row under
it (see [The fork server](05-workers.md#the-fork-server)).

**Drain** is on a worker that isn't drained, and **Resume** on one that is, while its
state is `active`, `draining` or `disconnected`. A worker that is `offline` or `lost` is
gone, and has neither. Drain is the maintenance command `schedr workers drain` (see
[Draining](05-workers.md#draining)): no new tasks, the ones it runs finish, and the drained
state is kept across its restarts until Resume. Resume means it takes tasks again. Both go through the
same dialog and result as the other actions (see [Actions](#actions)).

The UI asks every deployment at the same time, as on the DAG list, and gives up after the
same waits: 5 s to connect, 30 s for the request. One that can't be reached, or that
answers with an error, is named in a warning (`Unavailable: <name>: …`). The workers of
the others are still listed. When the deployments that answered have none, the page says
"No workers." The list updates while it is open (see [Live updates](#live-updates)). A
later update asks again for a deployment that was unavailable.

## Light and dark

A button at the right of the header switches between a light theme and a dark theme. The
choice is remembered in the browser and applied as the page loads, before it is shown.
Before a choice, the page follows the system's light or dark setting. Colour marks states
and warnings.

## Times

A time is shown in UTC and in the browser's zone, for example `2026-10-15 01:00 UTC · 03:00
CEST`. The local date is included when it differs from the UTC date. When the zone is UTC,
only the UTC time is shown. Seconds appear when they are not zero. On a schedule, the
window's bounds stay in the short form the CLI uses: UTC, with the browser zone's offset
once that zone is known (`2026-01-01 00:00Z (local:+1h)`). Until then the offset is left
out.

The page reads the browser's zone and remembers it. The first view is UTC only, and a note
at the bottom says "Times in UTC (the local time zone isn't known yet)." It then loads once
more, so the same page shows both. If the browser stores nothing, the note stays and the
times stay UTC.

## A path prefix

A gateway that serves schedr under a prefix and removes it sets `X-Forwarded-Prefix`. The
chart's VirtualService does (see [Deployment](10-deployment.md#inside-an-istio-mesh)). The
UI's links, the stylesheet, the live streams and `/docs` included, start with that prefix.
The prefix has to be a plain path: a `/`, then letters, digits, `-`, `_`, `.` and `~`, with
no `..` and no `//`. A trailing slash is dropped, so `/service/schedr/` is `/service/schedr`. Anything else
is ignored, and the links start at the root. Each answer carries `Vary: X-Forwarded-Prefix`,
so a cache keeps one copy per prefix.

## The documentation

`/docs` serves the documentation: this guide, Writing DAGs, the design log and the generated
reference. It is separate from Swagger UI at `/api/v1/docs/`, which describes the REST API.
The header links to `/docs` when the documentation is served. `/docs` redirects to `/docs/`
so the site's own relative links work, and the redirect keeps the path prefix. Only files
inside the documentation directory are served.

Both images include that site at `/usr/share/schedr/docs`, which is the default of
`[ui] docs_dir`. It is the site `make docs` builds, without the Rust API reference. Set
`docs_dir` to `""` to serve none. A path that is empty or not a directory also serves none:
the UI still starts, and the header has no Docs link. A `schedr` you built yourself has no
such directory until `docs_dir` points at one, for example `site` after `make docs`.

## Settings

`schedr ui` reads `[ui]`. It needs no database. It is ready once it listens, on the usual
ops port (see [Observability](09-observability.md)), and it has no loop of its own, so it is
alive while it answers. Ctrl-C or SIGTERM stops it.

| Key | Default | Meaning |
|---|---|---|
| `bind` | `0.0.0.0` | The address `schedr ui` listens on. Beyond localhost with `[ui.auth] mode = "none"` it warns that it signs no one in. Set `127.0.0.1` to keep it on the machine. |
| `port` | `8082` | The HTTP port of `schedr ui`. |
| `deployments` | none | Required. Each entry is a name, the webserver's URL and, where the UI proves itself by a token, its `token_file` (see [Sign-in](08-network.md#how-schedr-ui-proves-itself-to-a-webserver)). A name is letters, digits, `-` and `_`. It is shown, and it is in the UI's URLs, so each name is given once. With no list, or a name that breaks those rules, `schedr ui` refuses to start and says what to fix. |
| `auth` | `mode = "none"` | `[ui.auth]`: how people sign in at the UI (see [Sign-in](08-network.md#webserver-auth-and-ui-auth)). |
| `docs_dir` | `/usr/share/schedr/docs` | The documentation served at `/docs`. `""` serves none. |

Standalone uses `docs_dir` only. It ignores `bind`, `port` and `deployments`: the UI is on
the REST API's address, and the deployment is `default`.

```toml
[ui]
bind = "0.0.0.0"
port = 8082

[[ui.deployments]]
name = "etl"
url = "http://schedr-webserver.etl.svc:8080"

[[ui.deployments]]
name = "ml"
url = "http://schedr-webserver.ml.svc:8080"
```

The URL is the webserver's REST API (`http://schedr-webserver:8080`). It is contacted when a
page is opened. A wrong URL shows that deployment unavailable and leaves the UI running. The
[configuration reference](../_generated/04-reference/01-configuration.md) lists the keys.
Running it, and where standalone puts the pages, is
[Deployment](10-deployment.md#running-schedr-ui).
