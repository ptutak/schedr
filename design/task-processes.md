# task-processes

Rust/Python integration, how tasks start (fork server), the runner.

Generated by `make records` from the decisions whose `topic` (or `also`) is this one; edit the decisions, not this page.

## Current

### Runner and channel

- **A shim per task reports its start and exit** (D13): The fork server forks a shim for each task;
  the shim creates the task’s process group and reports its PID and exit. It reaps the task only
  after the agent closes the status socket.
- **The shim reports process usage without controlling the task** (D14): The shim reports core dumps
  and process usage with the exit status. If usage cannot be read, it reports null and still reports
  the exit.
- **Spawned process usage is read before the process is reaped** (D18): The agent reads CPU time and
  major faults from the spawned process’s zombie. Peak RSS and context switches are null; unreadable
  usage is null.

### Starting Python

- **Forked tasks run their own interpreter shutdown steps** (D15): Before exiting, a forked task
  waits for non-daemon threads and runs its own exit handlers. Inherited server handlers are
  cleared; logging shutdown and task finalizers are retained.
- **The fork server agent work is a separate plan step** (D17): M2.5.4 is split in two; M2.5.4a
  builds the agent side of the fork server. It starts and supervises fork servers and handles fork
  requests and fallback.
- **Retry fork server preload import failures for a limited time** (D19): Preload import failures
  are retried with backoff for `[worker] fork_server_import_retry`, default 20 minutes. After that
  the server stays disabled until restart; 0s disables retries.
- **Do not retry fork server thread or version failures** (D20): A disabled fork server is not
  retried for threads after preload or a version mismatch. The log reports failures and the disabled
  metric stays visible.

### Commands and supervision

- **A cancelled process group keeps its remaining grace period** (D100): If the main process exits
  during cancellation, remaining group members keep the rest of the grace period, then are killed.
  The stop ends at once when the group is empty.
- **A task's timeout counts from its launch** (D116): Timeout covers the whole attempt: secret and
  connection reads, runner or command startup, fork- server waits and request sending. The process
  receives only the remaining budget; exhaustion before launch starts no process and ends timed_out,
  removing connection files. Timeout or cancellation before hello stops the runner and ends the
  attempt accordingly.
- **Attempt timeouts include secret and connection reads** (D213): The attempt timeout includes
  secret and connection reads and runner or command startup. The process receives only the remaining
  time. If reads exhaust it, no process starts: the attempt ends `timed_out` and its connection
  files are removed.

### Interpreters

- **A worker's interpreters serve all its roots** (D385): A worker has one set of interpreters for
  all its DAG roots, never one per root. Workers are cheap: a different set of interpreters is a
  different worker with its own queues.

### Extensions

- **Extensions: a task kind run by a plugin executable the open worker supervises** (D510):
  `TaskKind::Extension { name, version, payload }`: a JSON payload under the DAG's limits, its
  output typed as for any task, stored and sent untouched; on the master an ordinary slotted task.
  The open worker runs it with a plugin executable it starts and supervises as it does the Python
  runner (timeout, cancel by SIGTERM then SIGKILL after the grace, the memory watchdog, stdout and
  stderr into the log, the `SCHEDR_*` variables); no fork of the worker. A worker knows its plugins
  from its config (a path and the versions each serves) and, opt-in (`[extensions] discover =
  true`), from each `schedr-ext-*` on `PATH` run with `--describe`, config winning;
  `Register.extensions` announces them (protocol 2.2), validation warns when none offers a DAG's
  extension and version (matched exactly), and a worker without it rejects the task
  (`REJECT_REASON_EXTENSION_UNDEFINED`, no try), the master trying another and ending it
  unschedulable once each has. Routing stays by queue. The plugin speaks the runner protocol over
  the inherited `SCHEDR_AGENT_FD`: a handshake naming its protocol version first (one the worker
  doesn't speak refused), then `extension_task`; it may ask what the Python runner may (the secrets
  and connections it declared, API calls, handles) and ends with `task_succeeded` or `task_failed`.
  The contract is those messages: a plugin is its own process (any language), counted in a task slot
  (decision note 15: no watcher-slot form, as decision 512 rules out work sharing a process). The
  Python helper's API is a coroutine (`async def run(request, channel)`) its `main` runs in a
  process. A plugin registers handles as it runs, and after any end of the attempt, a lost worker's
  too, the worker runs the plugin's cleanup with them (`extension_cleanup`), as a Python task's
  cleanup: what a `@sensor` can't (no `cleanup=`, no handles, decision 323). For authors:
  `schedr.extension` (Python) and a published Rust crate of the protocol's types and loop; an
  example plugin, a Python dummy, a worker test. *Corrected by DN15:* Extensions run only as their
  own process: no watcher-slot form. *Added to by DN17:* The Rust plugin crate stands on its own: no
  internal crate published with it.
- **Plugins observed and controlled as tasks are: status, links, declared metrics stored as worker
  samples, stop reasons, an Extensions page** (D513): A plugin gets the observability and control of
  a task, and more, through protocol 1 (unreleased: extended freely): a `status` message (phase,
  message, progress) and `links` (label, URL) shown on the task and the Extensions page; its own
  metrics, counters, gauges and histograms with declared buckets, each declared (name, kind, help,
  label names) in `--describe` or config, undeclared ones dropped with a warning; carried as
  workers' and tasks' figures are today (the heartbeat, minute samples, 15-minute rollups), charted
  on a UI page for all extensions and on the worker's Prometheus `/metrics`; and stop reasons kept
  within strict turns: SIGTERM to the plugin's process group as for any task, SIGKILL after the
  grace, and a plugin wanting the reason asks `stop_reason_get`, answered with it (cancel, timeout,
  drain, a lost master) and the grace left; the worker never sends an unasked message. Before R1.2
  (M5.2i5); the Kubernetes plugin uses every part. Settled: metrics carry the extension's own labels
  only (no DAG or task ID); declared in the plugin's `hello` (as NETCONF's hello announces its YANG
  models; `--describe` stays for discovery only, nothing run at a worker's start) and in config,
  config winning, kept per extension and version; status kept as a history of phases with their
  times; links sent whole by the plugin (its own options give base addresses), shown only for `http`
  and `https`; the Kubernetes plugin on a drain deletes its Job (retried elsewhere). Each extension
  has its own page: the author declares its panels (a title, a metric, one of our chart kinds: line,
  rate, stacked, histogram, quantiles, a number, a table by label) and its place in a layout of
  numbered rows of a fixed height (from 1 at the top), each one cell (`full`), two (`left`, `right`)
  or three (`left`, `center`, `right`); an `events` panel, no metric, shows the extension's own
  events and its attempts' latest phases (no log cells: a log is its worker's file); nothing of
  style but colour: a panel, or each of its series by a label's value, may name one of 20 colours
  schedr provides, each made for both the light and the dark mode (no other colour); every panel's
  place declared, and a metric no panel shows gets a `full` row of its own below them, one under
  another, as on the Metrics page; an events panel only where an author declares one; below them,
  its workers, versions and attempts. Metrics both ways: the worker's Prometheus `/metrics`, and
  stored per minute and rolled up per kind (a counter's growth summed; a gauge's average and peak; a
  histogram's bucket counts, sum and count summed over workers). The page and its API: the header's
  Extensions → `/extensions` and `/extensions/<name>`; `GET /api/v1/extensions`,
  `/api/v1/extensions/<name>`, `/api/v1/extensions/<name>/metrics?range=`; an attempt's statuses and
  links in the attempts API. Series bounded: at most `[extensions.<name>] max_series` (100) per
  metric, applied by each worker and by the master across workers (and on `/metrics`); a new label
  combination past it is folded into one `other` series, never dropped, with one warning and a note
  on the extension's page; a label may list its allowed values in its declaration, any other value
  counting as `other`. *Added to by DN19:* An events panel shows the worker's events for the
  extension, its attempts' phases, and its plugin's declared events. *Added to by DN21:* The
  Extensions page in tabs, one per extension; inside, all workers and each worker.
- **Chart functions: point, combine, group_by and limit** (D516): An extension's panel may name four
  functions saying how its metric is drawn, each with a default, so most panels name none. `point`:
  how one point is worked out from its bucket (a counter `increase` by default, or `rate`; a gauge
  `mean` by default (DN26), `last`, `max` or `min`; a histogram its `count` by default, `mean` or
  `quantiles`). `combine`: how values are combined, the workers' on the "All workers" tab and the
  labels left out of `group_by` (`sum` by default, `max`, `mean`, `min`): a value every worker reads
  from one place (a cluster's pending pods) declares `max`, so 3 workers reading 10 show 10, not 30.
  `group_by`: the labels that get a line each (all by default, a list, or none). `limit`: how many
  lines are shown, the largest by their peak over the range; the rest go into `other`. For example
  `{"metric": "pods_pending", "point": "max", "combine": "max", "group_by": ["namespace"], "limit":
  5}`. Not chosen: `over_time`, `across`, `by` and `top` as the names; one line in words (`"show":
  "max per namespace, top 5"`); a subset of PromQL; plain `fn`, `group` and `limit` keys. *Corrected
  by DN26:* A gauge's default point is its mean. *Not found in the code yet:* `over_time` (a name
  not chosen); `pods_pending` (an example metric).
- **An extension's service: one long-running process per worker beside its plugins** (D518, planned
  (M5.2i9)): Beside its per-attempt plugins, an extension may have a service: one long-running
  process per worker for what its attempts share (a client, a watch, a warm session), configured as
  `[extensions.<name>] service = ["cmd", ...]` beside `command`; without it nothing changes. Any
  program speaking our protocol over its control socket (`SCHEDR_SERVICE_FD`); in Python the
  functions of `schedr.extension`: `serve(on_call, start=, on_closed=, stop=, name=, versions=)`. It
  says `hello`, then `ready` within `service_ready_timeout` (60 s; else a crash); the worker offers
  the extension's versions only while it is ready, only those it serves. Each attempt gets a private
  connection (option C): a socket pair, one end the plugin's, the other passed to the service with
  `attempt_connected {attempt_id, task, version}`; a plugin reaches only its own extension's service
  (`await channel.service.call(...)`, an error without one), the worker not in the data path. A
  crash (or memory past `service_memory`, 256 MiB by default: DN25) closes the attempts'
  connections, their plugins failing them (retries apply), offers withdrawn until ready again,
  restarted backing off 1 s to 60 s; past `service_restarts` (5) within `service_settle` (24 h) the
  extension is turned off on that worker. Its secrets declared in config (`service_secrets`),
  fetched by the worker; its output in the worker's log, tagged; starting, ready, restarts and
  turned off as events; its statuses and metrics over the control socket. A loop stalled past 5 s is
  warned of (logged and an event). On a drain or turned off: no new attempts, SIGTERM after the last
  connected one ends, SIGKILL after the grace. One per worker (N workers, N clients); recovery stays
  the cleanup handles'. Not chosen: through the agent, a socket path; declared in `--describe`;
  decorators (`Service` with `@service.call`); a probe for readiness; attempts reconnecting after a
  restart; one shared across workers. *Corrected by DN25:* A service's memory 256 MiB by default.
- **Shell plugins: declarations in config, configured only; status and link for command tasks**
  (D519): For shell plugins (`schedr extension shell -- <script>`): their metrics and panels
  declared in `[extensions.<name>] metrics` and `panels` (a script sends no hello); configured
  extensions only, no discovery; `schedr task-ctx stop-reason` prints the reason and the seconds
  left after SIGTERM. Command tasks get `schedr task-ctx status` and `link` too (shown on the task
  panel); `metric` only within an extension, a command task told so (no declarations, no page). Not
  chosen: metrics for command tasks; a `--declarations` file; a discoverable shebang
  (`#!/usr/bin/env -S schedr extension shell --name ...`); a reread environment file. *Corrected by
  DN27:* A shell plugin's own commands sit under `task-ctx extension`.
