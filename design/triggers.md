# triggers

## Current

### One trigger

- **A trigger runs as a hidden sensor without an attempt** (D348): A trigger runs on a watcher slot
  as a hidden sensor, without a graph node or attempt. Events are acknowledged after storage; the
  trigger resumes from its bookmark and restarts on code changes.
- **`EventNamed` waits for events posted through the API** (D354): Named events can trigger DAGs or
  be awaited by nodes, sensors and trigger functions. Waits match events posted since run creation;
  triggers start at most one run per name and key.
- **A DAG's trigger has its own row with its switch; no row, no trigger** (D459, planned (1.0.0)):
  Pausing switches a DAG's trigger off; manual runs start either way. The switch is the trigger's:
  `dag_triggers` holds a row per DAG whose current code has a trigger (its kind, `paused`,
  `live_since`), and no row means none (`dags` has no `paused`). A parse gaining a trigger, or
  changing its kind (Schedule, Run of, Chained, Event, as the UI names them), stores it paused;
  another trigger of the same kind keeps the switch; losing it deletes the row. Pause and unpause
  are refused without one. The API's `trigger_state` is `paused`, `active` or null; `dags list`'s
  STATE is `paused`, `active` or `manual`; the UI shows the kind and the switch (`active` or
  `paused`) in one Trigger column, no State column. `triggers` and `trigger_passed` are renamed
  `trigger_progress` and `trigger_progress_passed`. Not chosen: the flag on `dags` (it isn't the
  DAG's); resetting on every trigger change (a cron edit would pause production); a stored `manual`
  (a second copy of the code's fact); a 0002 migration (only rc1's test databases exist).

### `@trigger` and `@trigger.poke`

- **Trigger failures, stopping and restarts retain their state** (D349): Poke errors retain the
  bookmark; returned generators stop until code or version changes. Queue limits and idle restarts
  govern running triggers, whose strikes and consecutive errors persist.
- **`@trigger.poke` batches events in Python** (D352): `@trigger.poke(batch=...)` gathers a window
  in Python and stores each item individually. One run receives only its new items as
  `list[Event[T]]`, keyed by the last new item; no new items means no run. The bookmark advances to
  the window's last key, including a repeat. Replaying an individual key produces a singleton batch.

### Manual runs, CLI and tests

- **Triggers have endpoints, manual event runs and test helpers** (D350): Trigger API and CLI
  endpoints show, restart and switch on triggers and list events. Manual runs supply an event; test
  helpers and the DAG page expose trigger events.

### Cycles

- **A cycle through trigger=RunOf across DAGs isn't caught** (D394): A cycle of DAGs started by
  `trigger=RunOf(...)` isn't detected (those runs have no parent chain to check); the docs warn
  about it. TriggerDagOperator's cycles are caught.

### Placement and ordering

- **The trigger loop runs after any write, at a stored moment, or for a posted event** (D486): The
  trigger pass runs in a loop of its own beside the round (decision 485), woken when a write ended
  in this master outside `Database::quietly` (a worker's message, a round's work, a stream ending;
  not the lease, the node row, heartbeats, the outbox, retention), when a named event its triggers
  wait for is posted (Postgres: `EVENTS_CHANNEL`, announced only when something waits; the post
  clears those triggers' stored look), and by the tick's probe when a trigger's stored moment
  (`next_fire_at`: the earliest of its window's edges, a restart's backoff, a generator's
  `restart_if_idle`, written only by the loop) has come or isn't known; also when a trigger's state
  changes in memory (`trigger_wake`: a call done, a stop's ack, a slot freed) and at the next tick
  after a failed pass. A pass first claims the looks not known (`claim_looks`) and stores a new one
  only over the value it took, so a post during the pass stays seen. At most one pass every 50 ms,
  skipped by one `EXISTS` when no trigger is switched on or running. A pass that wrote wakes the
  round (option A of 2026-11-14). Not chosen: a wake at each place an input changes (one forgotten
  leaves a trigger stuck).
- **A waiting wait_for step stores its deadline and what it waits for** (D487): A `wait_for` step
  the master holds (another DAG's run, or a named event; no worker, decision 380) is no longer
  looked at every tick while it waits: before each look it is parked: `look_at` is its `max_wait`
  deadline (the ready check skips it until then), and `waits_dag` or `waits_event` name what it
  waits for. That DAG's run or task ending (row triggers on `state`, both backends), that event
  posted, or its own state changing clears `look_at`, so the next round's probe finds it. Not
  chosen: the deadline alone, re-checked on any write (a busy master would look at every waiting
  step on every write).
