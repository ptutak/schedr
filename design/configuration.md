# configuration

The configuration file, keys, env, hidden keys, timings.

Generated by `make records` from the decisions whose `topic` (or `also`) is this one; edit the decisions, not this page.

## Current

### Effective configuration

- **Show each deployment node's effective configuration masked at source** (D122): Each node
  supplies its own effective configuration for the API and Deployments page. The node masks secrets
  before its configuration leaves the process.

### Timings and limits

- **Deployment-dependent timings are configuration keys** (D231): Timings whose right values depend
  on the deployment are public keys. Each key has a doc comment describing its effect and when to
  change it.
- **Hidden environment variables change fixed timings** (D233): `SCHEDR_HIDDEN__<SECTION>__<NAME>`
  changes a fixed timing at startup. Each setting is warned about; unknown names and invalid
  durations stop startup, but for the retired quiet-DAG timings (`RETIRED_TIMINGS`, decision 485),
  accepted and ignored.
- **Hidden timings cannot be zero** (D234): Every hidden timing must be nonzero. A zero hidden
  timing is refused.
- **Per-task cleanup defaults to the worker cleanup timeout** (D235): A per-task cleanup without its
  own timeout uses `[worker] cleanup_timeout`; the DAG JSON omits `timeout_ms` and the worker
  supplies it. Resource cleanups instead default to `[worker] resource_cleanup_timeout`, 30 minutes
  per try.
- **New configuration values are public or hidden** (D237): A new value is a public key when
  deployment determines its right value; otherwise it is hidden. A binary constant requires a really
  good reason.
- **Public timings that cannot work at zero are refused** (D238): Public timings that cannot work at
  zero are rejected during configuration load. Timings where zero has a defined meaning remain
  allowed.
- **DAG parse concurrency defaults to four files** (D332): [dags] parse_concurrency defaults to 4
  concurrent spawned or forked parses, capped at the cores the agent may use; 1 parses sequentially.
  dags check uses it and forks when the interpreter has a fork server. Parsing consumes no task
  slots; each process has its own memory budget.

### Sources and validation

- **Eighteen fixed timings leave the configuration** (D232): Removed configuration keys:
  `tick_interval`, `heartbeat_interval`, `lease_timeout`, `lease_period`, `read_back_window`,
  `read_back_interval`, `query_timeout`, `loop_stall_timeout`, `set_aside`, `listen_retry`, the
  three quiet-DAG timings (retired since decision 485), `refresh_interval`,
  `worker_connect_timeout`, `drain_report_period`, `memory_check_interval`, `handshake_timeout`.
  Setting one in a file or through `SCHEDR_CONFIG__*` fails as an unknown key; there is no
  migration.
- **Fixed timings are passed in per-crate structs** (D236): M4.8u passes hidden timings through each
  crate's own struct with defaults in the server, worker and webserver, including `auth_remembered`
  and `auth_recheck`. The client, `task-ctx` and the CLI's commands don't use these timings (the
  binary reads the configuration file for every command but `task-ctx` and `dag-ctx`).

### Hidden timings

- **Auth timings use the hidden configuration** (D239): `auth_remembered` and `auth_recheck` use
  hidden timing values. Changing the users file forgets remembered checks; `auth_recheck` sets the
  change delay.
- **Inline server timings use the hidden configuration** (D240): Hidden timings include Vault
  renewal waits, a stopped group’s poll, and connection-test cancel grace. They also include
  listeners’ retry after a failed accept.
- **Some timings remain constants** (D241): The production gauge-refresh limit is half of
  `loop_stall_timeout`. Migration-connection timings remain fixed, without `query_timeout`; client,
  `task-ctx` and CLI timings also remain constants.
