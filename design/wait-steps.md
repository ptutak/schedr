# wait-steps

Sensors, wait steps, the watcher host, `first_of`, `delay` / `until`.

Generated by `make records` from the decisions whose `topic` (or `also`) is this one; edit the decisions, not this page.

## Current

### The watcher host

- **A watcher host serves one interpreter and code set** (D320): A watcher host holds one
  interpreter and set of root copies; new code uses a new host. Pokes move between calls after
  successful preparation, preserving deadline and retries, or remain on old code with a logged
  reason; full-control sensors remain until completion. Old hosts exit when empty, and memory_budget
  covers all worker hosts.
- **Watcher hosts stop when their last watcher ends** (D334): A watcher host is spawned, never
  forked, and stops when its last watcher ends. Successful DAG imports are reused within the host;
  failed imports are retried for the next attempt. Its working folder is the worker log folder and
  its environment is the allow-list plus `pass_env`; wait steps obtain run values from `dag_ctx` and
  `task_ctx` and use absolute paths.
- **A poke moves to new code only when it can continue** (D335): A poke finishes its current call
  and moves to new code without a retry or deadline change, if the new host can prepare it;
  otherwise it stays on old code. Full-control sensors stay until they end.

### What a wait step is

- **A wait step keeps its deadline across retries and moves** (D321): The max_wait clock starts at
  the instance’s first start and continues across retries and moves. A wait that runs out of time
  ends with TimedOut, including while waiting to run again.
- **A poke that exceeds every fails** (D322): Each poke call is limited to every and calls do not
  overlap. A call that runs out of that time is cancelled and fails with a clear message.
- **Wait steps do not accept task cleanup options** (D323): Wait steps accept applicable task
  options, using max_wait instead of timeout, and excluding cleanup and its settings, preload and
  fresh_process. Cleanup options cause a parse error directing the author to finally.
- **A wait step’s plain >> runs on its value** (D324): A wait call reads as Waited[T], containing
  its value or TimedOut; passing it directly to a parameter accepting only T is rejected. Select the
  value with .on(T), the timeout with .on(TimedOut), or accept both explicitly. Plain >> selects the
  value; failed waits propagate upstream_failed, with ordinary run_if rules for untaken edges.
- **Wait steps use max_wait and shared StepDefaults** (D325): Wait steps use max_wait and tasks use
  timeout; supplying the other kind’s key is an error. StepDefaults replaces TaskDefaults without an
  alias and supplies shared settings for both kinds, with each limit applying only to its kind. Wait
  limits follow step, group, DAG, then [sensors] default_max_wait precedence.
- **A timed-out wait step is grey and leaves its run successful** (D344): A running wait step pulses
  unless reduced motion is requested; a failed one is red. A timeout is grey and says `TimedOut`,
  and the run stays successful.

### What a wait step may start

- **A wait step cannot start a process or thread** (D336): At DAG definition, process and thread
  creation in the author's code, including its own helpers and classes, is rejected. Runtime process
  creation is refused in inherited step contexts, except for the standard-library `platform`,
  `ctypes.util` and `uuid` helpers; library threads and `asyncio.to_thread` are allowed. This is not
  a sandbox: C code can bypass enforcement. Leftover asyncio tasks are cancelled and awaited.
- **A wait step owns its `asyncio.to_thread` calls** (D337): `asyncio.to_thread` calls run in their
  wait step’s context and are tracked. Calls still running at cancellation or step end are stopped;
  a stuck thread ends with its host.
- **Library threads in watcher hosts are watched** (D339): Library threads are allowed and a thread
  alone is not a strike. A Python thread still alive at step end is logged; host thread counts are
  shown as tied and untied, and as a metric.

### The 30-second rule

- **Repeatedly blocking wait steps and triggers are switched off** (D338): Consecutive blocking
  strikes switch off a sensor or trigger after `[watchers] switch_off_after`. Success clears
  strikes; a command or new code switches it on, with one chance for new code.
- **Watcher host failures blame the responsible step when identifiable** (D341): A step responsible
  for a blocked loop, stuck thread or ignored cancellation is blamed. Other watchers restart in the
  same attempt; unidentifiable host loss uses retries.
- **Watcher host crashes and memory kills are visible as losses** (D342): Crashes and memory kills
  blame no wait step and switch none off; each lost attempt uses a retry. The error names the host’s
  wait steps and a metric counts losses per code set.

### Nodes the master ends

- **`first_of` and `at_least` select completed outcomes** (D347): Master-ended `first_of` yields the
  first taken edge's value; `at_least(n, ...)` yields the first n values in completion order, with
  `with_winner=True` also supplying IDs. `first_of` is skipped if all edges are not taken, or
  becomes `upstream_failed` if an edge failed and none can still succeed. Losers continue; a failed
  loser still fails the run without changing the completed node or its downstream results.
- **A graph groups `first_of` options in a box** (D351): The graph draws `first_of` options in one
  box with a dashed edge to the node, highlighting the winner. Where a box cannot be drawn, options
  have separate dashed edges.

### `delay` and `until`

- **`delay` and `until` are plain Python wait steps** (D355): `delay` waits from the first try’s
  start; `until` waits for a planned-time offset or aware datetime. Both return the moment they end,
  and retries of `delay` wait only the remaining time.

### Built-in waits

- **No by_deadline wait** (D392): `delay` and `until` are the built-in waits; there is no
  by_deadline wait.

### first_of

- **first_of doesn't cancel the tasks that didn't win** (D393): After `first_of` ends, the tasks
  that didn't win keep running, and one that fails still fails the run; there is no option to cancel
  them.
