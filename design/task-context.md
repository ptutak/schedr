# task-context

The in-task CLI, run parameters, `dag_ctx` / `task_ctx`.

Generated by `make records` from the decisions whose `topic` (or `also`) is this one; edit the decisions, not this page.

## Current

### `dag_ctx` and `task_ctx`

- **Task context exposes the running instance identity** (D84): `task_ctx` exposes `task_id`,
  `try_number` and `map_index` while a task runs. The map index is `None` for an unmapped task.
- **Async in-task calls use an a prefix** (D315): Async tasks can await task_ctx.asecret,
  task_ctx.asecret_value and acleanup_handle. Sync calls remain available and block the event loop
  while waiting.
- **Tasks call schedr’s REST API through their agent** (D356): `schedr.api` sends allowed task and
  trigger requests through the agent to the master’s API. Outside a task it uses HTTP; local DAG
  tests use their standalone master and database.

### Parameters

- **Run parameters precede the agent channel and UI trigger form** (D132): M4.5a builds parameter
  declaration, validation, storage, CLI and test inputs, references, typed access and the run
  summary. M4.5b builds the agent channel; M4.5c builds the UI trigger form.
- **The master checks run parameters and their schemas with jsonschema** (D133): The master
  validates values with jsonschema, with formats checked and remote references disabled. DAG
  validation accepts only supported schema keywords and formats, annotations and local references;
  other keywords are DAG errors. Pydantic validators run when a task decodes values.
- **Run parameters are masked when shown** (D134): Shown parameters are masked like task outputs;
  tasks receive originals. Refusals never quote parameter or schema values, mask names, and omit
  even the keyword beneath secret-named fields. The webserver rejects NUL before storing a command;
  run-DAG views retain only masked parameter defaults. Bad bodies, `-p`, invalid dataclass defaults
  and Pydantic default serialization produce no value- bearing diagnostics; invalid dataclass
  defaults also omit their type.
- **Run parameters are limited to 64 KiB of JSON** (D135): A run's parameters, including defaults,
  may occupy at most 64 KiB as JSON. An oversized set is refused at trigger time; a DAG with
  oversized defaults is refused at parse time.
- **A queued run keeps its validated parameter values** (D137): A queued run keeps the values
  validated against the version on which it was created. They are not checked again when it starts.
- **Run parameters are described in DAG JSON and stored as tagged values** (D138): DAG JSON carries
  the parameter type, JSON Schema and defaults. The master fills defaults, refuses unknown keys,
  validates values and stores them as tagged outputs; scheduled runs use defaults.
- **Durations may be given in weeks** (D139): ISO 8601 durations may use weeks, each a fixed seven
  days. Years and months remain refused.
- **A whole number with a fraction fits an integer parameter** (D140): A whole number written with a
  fraction, such as `1.0`, fits an `int` field. It is stored as `1`.
- **The master checks duration formats as ISO 8601** (D141): The master checks `format: duration`
  itself as ISO 8601. It accepts fractions of a second, including Pydantic timedelta values.
- **Trigger-time parameter values are masked** (D142): Trigger-time values are masked in refusals,
  run views, errors and logs; stored parameters and defaults are shown masked. Code-authored text is
  shown as written where code is shown.

### Inside a command or a script

- **Each context caller sends its own socket end** (D143): Command-task processes inherit the
  datagram channel named by `SCHEDR_CTX_FD`; each caller passes one end of a fresh stream socket
  pair through `SCM_RIGHTS` and uses its own connection. It speaks length-prefixed JSON, beginning
  with protocol `hello`. The agent serves at most 64 connections open at once and refuses one more
  while they are; malformed descriptor messages are dropped and their descriptors closed. Linux and
  macOS are supported.
- **The context channel initially serves dag-ctx** (D144): `schedr dag-ctx` provides `params get`
  and `run get`, each with optional `--field`. Parameter values print in the JSON form accepted by
  `--params`.
- **schedr.script decodes run context values** (D145): In a command-task script,
  `schedr.script.dag_ctx` loads context on first read using one connection and two requests. Stored
  forms decode to native dates, timedeltas and tuples; object fields become dictionaries because the
  script does not know the declared class. `dag_ctx.params(Cls)` decodes strictly into the supplied
  class. Inside a Python task, its existing context values are used.
- **The context channel is inherited by command tasks** (D146): Command tasks and their child
  processes inherit the context channel. Python tasks use their own `dag_ctx`; a closed inherited
  descriptor is reported.
- **The context channel accepts callers by protocol version** (D148): The agent accepts context
  protocol 1 regardless of schedr version; `hello` supplies both, and incompatible-protocol refusals
  name both versions. Within a protocol, new requests and fields are allowed: unknown fields are
  ignored and unknown requests receive `error`. Other changes, including new enum values, require a
  new protocol.

### Unsafe code

- **The inherited descriptor uses unsafe code in schedr-fd** (D147): Only `schedr-fd` relaxes
  `unsafe_code` from `forbid` to `deny`, permitting its single unsafe site through `#[expect]`;
  every other crate retains `forbid`. It borrows the inherited descriptor solely to duplicate it
  close-on-exec, then validates the copy as a Unix datagram socket. It never owns or closes the
  inherited descriptor.
