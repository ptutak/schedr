# chained-runs

`TriggerDagOperator`, dependencies between DAGs.

## Current

### Waiting for runs

- **`RunOf` waits for or triggers from another DAG’s run** (D353): `RunOf` selects another DAG's run
  or task; lagged waits use this run's `planned_for` minus lag and choose the newest matching run by
  `triggered_at`. The master-ended node yields a run ID or `TimedOut`; failed, cancelled or skipped
  targets yield routed `Failed`, otherwise failing the node and run. No-code triggers start runs
  only for successful completions while live, without catching up paused periods. Function sensors
  and triggers receive `RunResult[T]` on watcher slots for all terminal states; sensors may return
  `NOT_YET`, and failed calls retry the same handed run, with trigger retry limits or manual skip
  available.

### Building it

### TriggerDagOperator

- **`TriggerDagOperator` gives the target run’s ID** (D358): The operator’s value is the target
  run’s ID, whether or not `wait=True`. The target’s output can be read with a `RunOf` sensor or the
  API.
- **A failed target gives a routable `Failed` outcome** (D359): A failed, cancelled or skipped
  target gives `Failed`, including its state. The DAG can route it with `.on(Failed)`; otherwise the
  operator task fails.
- **`max_wait` times out without cancelling the target run** (D360): When the operator’s `max_wait`
  expires it yields `TimedOut`. The target run continues.
- **An operator retry starts a new run only after failure** (D361): A retry starts a new target run
  only after the previous run failed. The run's ID is recorded on the task's attempt first and the
  run created by that ID, so a master stopped in between creates it once, never two.
- **A triggered run accepts an optional `planned_for`** (D362): `planned_for` accepts a datetime or
  a reference and defaults to the parent’s planned time. Airflow’s `logical_date` maps to it.
- **Tasks start runs with `TriggerDagOperator`** (D365): Tasks start runs with `TriggerDagOperator`.
  The task routes of `schedr.api` remain limited to events.
- **A missing or conflicting target fails the operator, with its retries** (D379): A
  TriggerDagOperator whose target DAG is missing or in an ID conflict when it runs fails with the
  reason, and the task's retries apply (the target's root may not be parsed yet). Invalid `params`
  still fail without retries.
- **A waiting TriggerDagOperator doesn't count towards the DAG's limits** (D380): A
  TriggerDagOperator holds no worker and no slot, and its attempt doesn't count towards
  `max_active_tasks`, `max_active` or `max_active_per_run`, as `wait_for` nodes don't. Replaces the
  earlier text that it counts as a running task.
- **Operators are mapped in a later step, TriggerDagOperator with them** (D381, planned (M4.12c)):
  No operator can be mapped yet (only `@task` functions have `.expand`); operator mapping, one
  design for every operator, is plan step M4.12c. Until then mapping a TriggerDagOperator is refused
  with a hint to create one per element in a `for` loop in the DAG file.
- **A TriggerDagOperator starts only a DAG with `trigger=Chained()`** (D398): A DAG's runs come one
  way: its own trigger, or other DAGs' TriggerDagOperators, which start only a DAG with
  `trigger=Chained()` (any DAG) or `Chained(by=[...])` (those named; `by=[]` is an error). Any other
  target fails the task when it runs (`chained_target_refused`, not retried); a paused one too, with
  retries. `schedr dags check` fails the operator's file when its target in the root refuses it; the
  master's parse doesn't. `trigger=None` means manual runs only: the UI greys out its Pause. Manual
  runs stay allowed on every DAG, a fallback and for testing. `schedr dags test` unpauses the
  `Chained` DAGs of the path tested.
- **Cycles between DAGs are allowed; only a cycle inside a DAG is refused** (D399): DAGs may start
  each other in a cycle, through TriggerDagOperators, `RunOf` triggers or events: no check follows
  the chain of parent runs. Inside a DAG a cycle is refused when its file loads: its tasks depending
  on each other, a TriggerDagOperator naming its own DAG, `Chained(by=...)` naming it. A run started
  by a `RunOf` trigger records the run that started it as its parent, linked both ways in the UI as
  a chained run is.

### Tests

- **In tests a TriggerDagOperator starts a real run of a target in the tested path** (D378): In
  `schedr dags test` and `run_dag`, a TriggerDagOperator starts the target's run on the local master
  when the target is in the path given (a DAG root); a target outside it fails the task with a hint
  that its DAG file must be in the path tested. There is no stub.
