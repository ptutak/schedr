# ui-cli

The web UI, the user CLI, the REST API.

Generated by `make records` from the decisions whose `topic` (or `also`) is this one; edit the decisions, not this page.

## Current

### Pages and live updates

- **Draw DAG graphs as server-rendered SVG with a layered layout** (D22): The server draws the DAG
  graph as SVG using its own layered layout. The layout performs layering, crossing reduction and
  x-placement.
- **The run graph flows from top to bottom** (D30): The run graph places layers down the page. Task
  names have the full width available.
- **Task details open beside the run graph** (D31): Task details load in a panel beside the graph
  using htmx. A task query parameter opens the same panel on a link or reload.
- **Merge runs from all deployments into one list** (D32): The runs list merges deployments and
  shows a Deployment column when needed. A shared cursor pages the list and filters apply to each
  deployment.
- **Show the last 64 KiB of task output** (D33): The UI shows the last 64 KiB of the pretty-printed
  task output and marks it as cut. The complete output is available for download.
- **Live events identify what changed** (D34): Live events identify the changed run, DAG or workers;
  the UI re-renders from the API. Postgres uses NOTIFY and the SQLite webserver polls about once a
  second.
- **Enable live change notifications by default** (D38): Database change notifications default on,
  including standalone. `[database] change_notifications` is applied by `schedr db migrate` or
  startup `--migrate`, holding the lease, never by a running master. The webserver follows the
  database’s trigger state; when off, it sends refresh events every 15 s (a hidden timing since
  D232: `SCHEDR_HIDDEN__WEBSERVER__REFRESH_INTERVAL`).
- **The run graph draws task groups as clustered boxes** (D65): The run graph orders each layer by
  group and draws nested, padded boxes around group members. The layout keeps unrelated tasks
  outside boxes and avoids overlaps. *Not found in the code yet:* the layout avoids overlaps.
- **Import errors show failed files of current parses** (D66): The API shows failed files of each
  root’s recorded current parse, including root, hash, per-file worker/time, exception, message and
  traceback. Their DAGs retain their last good version; non- transient errors hold them, while
  transient failures hold nothing and are retried. *Not found in the code yet:* a DAG keeps its last
  good version.
- **Import errors have their own page** (D67): An Import errors page sits beside DAGs, Runs and
  Workers and merges deployments. A navigation count and DAG-list notice load after the page.
- **Parse warnings stay in dags check** (D68): The import errors view reports errors; parse warnings
  such as `TypingHint` remain in `dags check`. Warnings are not uploaded for this view.
- **The run graph shows one node per mapped task** (D83): A mapped task has one graph node labeled
  with its instance count and counts by state. Its panel lists instances with their attempts, logs
  and outputs.
- **The DAG page shows concurrency limits with their current counts** (D96): The DAG page shows each
  configured concurrency limit and its current count. The counts are the open attempts in the
  database (`active_counts`); a reached limit says the rest wait.
- **Call the page Deployments** (D121): The page is named Deployments, matching the UI and its
  deployments configuration. It shows the deployments available to the UI.
- **Show the UI and all deployments in one graph** (D128): `/deployments` is one graph containing
  the UI and framed deployments, grouping nodes by process in standalone. Links show HTTP from UI to
  webserver, the database from webserver to masters, and gRPC from workers to their registered
  master, dashed when disconnected; workers show queues. Node panels show details and configuration
  as TOML, omitting unset values. The UI panel retains the Config page’s content; `/config`, its
  navigation entry, and separate deployment pages and routes are removed.
- **Live UI pages share one stream per browser** (D175): A SharedWorker distributes the deployments'
  changes to live pages, with replay or refresh. Without SharedWorker each page has its own stream,
  released after 10 seconds hidden. Running attempts' log tails are polled.
- **Show a resource as two caps joined by a rail** (D262): Setup and cleanup are named, coloured
  caps in a left-hand Resources box, one lane per resource, retaining their graph-row heights.
  Shared-group users get two summary lines; otherwise links reach first and last users. Remaining
  user links and the rail appear on hover or selection; cleanup-to- successor links remain visible.
  Lists show one row in two parts. *Not found in the code yet:* the caps keep their graph-row
  heights.
- **The graph shows which tasks a cleanup holds back** (D272): With `blocking=True`, draw downstream
  order edges from the cleanup cap and omit redundant user order edges; retain user data edges. With
  `blocking=False`, retain original task/group edges and draw the users’ link to the cleanup dashed.
- **The UI names a DAG's trigger kind, shows descriptions in the list, and offers no Pause for a DAG
  without a trigger** (D457, planned (1.0.0)): The DAG list's and the DAG page's Schedule becomes
  Trigger: the kind (`Schedule` for cron, every and once, `Run of`, `Chained`, `Event` for
  `@trigger` and `EventNamed`, `Manual` for none), then the trigger as the CLI writes it, nothing
  after `Manual`. The list shows a DAG's description under its id, one line, all of it on hover. A
  DAG without a trigger has neither Pause nor Unpause: it has only manual runs, which pausing
  doesn't stop (its switch, decision 459). Not chosen: the API's kind names (`Cron`, `Every`,
  `RunOf`, `None`); a greyed-out button.
- **A DAG page's actions are one row; Restart only for a trigger stopped, failing or stuck** (D461,
  planned (1.0.0)): Trigger, Backfill, Pause or Unpause, and an event trigger's Restart and Skip run
  share the page's one row of actions. Restart is shown only where it changes something: the trigger
  stopped, failing and waiting to start again, or stuck (a running poke trigger none of whose calls
  has ended for over three times its `every` plus a heartbeat; the API's `stuck`, `(stuck)` in
  `triggers list`). Not while paused (Unpause starts it) nor running well; a long-running trigger
  can't be told stuck (`restart_if_idle` restarts it). `schedr triggers restart` works at any time.
  Known limit: the poke's time is the worker's clock, so a worker off by more than the window
  (warned `clock_skew` past 2 s) can be shown stuck wrongly. Not chosen: Restart always shown;
  Restart for any running listener.
- **The Deployments page has a Status block above its graph** (D462, planned (M5.1g)): One row per
  deployment above the graph: masters by role (red when none leads), workers by state, slots in use
  over active workers, errors and warnings counted with the list unfolding (each line opening its
  node's panel), mixed versions warned, an unreachable deployment's error and how long it took. `GET
  /api/v1/deployment` gains each worker's `slots` and `running` (additive). Memory now, with a 24 h
  sparkline, joins it with the memory samples (decision 464). Not chosen: runs and tasks by state in
  the block (left to the Metrics page).
- **A Metrics page with memory and CPU over time** (D465, planned (M5.1j)): `Metrics` follows
  Deployments in the navigation (the UI's `/metrics`; the processes' Prometheus `/metrics` stays on
  their ops port). Per deployment, over 1 h, 24 h, 7 d or 30 d: memory and CPU charts of its
  processes (the 8 highest peaks, the rest as one band, container limits dashed) over a sortable
  table (now, peak, limit, share); a row opens a panel beside the chart with that process's
  breakdown and its largest tasks. A node's panel on Deployments gets a 24 h chart and a link; the
  Workers page a Memory column. Throughput and start latency by stage join after M5.1a-f.
- **UI charts are SVG drawn by the server** (D466, planned (M5.1j)): Charts are SVG rendered on the
  server like the DAG graphs (decision 22), with no JavaScript chart library: a point's value shows
  on hover from its `<title>`, and an open chart refreshes once a minute on the page's live stream
  (decision 175). Light and dark from the UI's colour tokens; on a phone charts stack and tables
  scroll in their own box. Not chosen: a vendored library such as uPlot (hover and zoom); Grafana
  dashboards in the Helm chart, for now.
- **A task's peak memory over its attempts is charted** (D467, planned (M5.1k)): The task panel
  charts the peak memory of a task's last 30 attempts from the attempts table, one bar per attempt
  coloured by its outcome (`oom_killed` marked) and linking to its run, its memory limit dashed. The
  DAG page lists its tasks' p95 peak against their limits, closest first.

### Access and authentication

- **The UI has no sessions of its own** (D24): Basic authentication uses the browser’s credentials
  and proxy-header authentication uses the proxy’s session. UI POST actions require matching
  `Origin` or `Sec-Fetch-Site` information.
- **Render the UI in Rust with htmx** (D26): Rust Askama templates render HTML and htmx supplies
  interactive partial updates. Assets are embedded in the binary and require no JavaScript build.
- **Serve the versioned documentation inside the UI** (D28): Images include the built Sphinx site
  under `/usr/share/schedr/docs`. The UI and standalone serve it at `/docs` when the configured
  directory exists.
- **Webservers accept forwarded identities only from a proven UI** (D36): The UI forwards the
  person’s name; webservers trust it only from a proven UI. Proof is mTLS with the UI certificate
  name on the dedicated port in app mode, the guarded mesh port where enabled, a shared token
  otherwise, or an in-process call from standalone’s own UI.
- **Keep user management outside schedr** (D39): schedr keeps no user database, user management UI,
  admin role or sessions. People remain with the organisation’s identity provider; Basic auth
  retains its users file for labs and single machines. A separate LDAP mode checking Basic
  credentials by directory bind is planned for M6.
- **UI proof follows the deployment TLS mode** (D40): Distributed app mode uses mTLS on the
  webserver’s UI port. Mesh proof uses that port over HTTP with `ui_port_in_mesh`, Istio
  authorization, a UI account shared with no other role, and a DENY policy excluding other callers.
  Standalones, mesh deployments without that policy, and shared-account setups use a token.
- **The UI and API use compatible sign-in modes** (D41): The UI and webserver use the same auth
  mode, or the webserver uses `none`. The distributed chart enforces these pairs and defaults UI
  auth to webserver auth.

### Actions and parameters

- **Confirm UI actions in an inline dialog** (D35): Actions use an HTML dialog describing what will
  happen. The inline result shows pending, applied or rejected with the master’s reason.
- **Store a command once per idempotency key and person** (D126): The webserver stores one command
  per Idempotency-Key and person, returns it for the same request, and answers 422 for another
  command under that key. The CLI creates a key per command; the UI creates one when the dialog
  opens and retains it in the tab until delivery is definite. Both make at most three attempts using
  that key after missing answers or server failures; the UI says unresolved delivery ‘may have
  arrived’.
- **The webserver describes the trigger form** (D149): The webserver builds `params` form
  descriptors for a single DAG view; the UI does not interpret JSON Schema. Fields describe their
  name, kind, requiredness, nullability, secrecy, default and Literal choices. Defaults and choices
  are withheld for secret fields.
- **Secret-named parameter fields use empty password inputs** (D150): A field is secret when its
  name contains a secret word or its default or a choice contains a secret. It uses an empty
  password input, with defaults and choices withheld from the browser. Its default is excluded from
  the form fingerprint; leaving the input empty sends nothing, so the master supplies the current
  default.
- **Optional parameter fields have a none checkbox** (D151): An optional parameter field has a
  `none` checkbox beside its input. An empty string remains a value for an optional string.
- **Complex parameter fields use JSON text boxes** (D152): A nested model or dataclass, list or dict
  uses a JSON text box. It is pre-filled with its default as JSON and checked by the master.
- **A stale trigger form is refused** (D159): The trigger form carries a fingerprint of the fields
  and defaults it displayed. If they changed, triggering is refused and the page must be reloaded;
  secret defaults are excluded.

### REST API and CLI

- **The REST API identifies mapped instances by map index** (D71): A run’s tasks include rows for
  mapped instances, identified by `map_index`. Per-instance operations use `?map_index=N`; unmapped
  tasks use index -1.
- **The API lists the mapped task before its instances** (D80): The run’s task list includes the
  whole mapped task’s `-1` row, its instance count and any failure reason. Its instance rows follow
  in map-index order.
- **Mapped output defaults to the gathered list** (D81): Without `?map_index`, the API returns the
  gathered list, with `None` for skipped instances. With an index it returns that instance’s output
  and outcome.
- **Mapped task operations accept an instance index** (D82): Attempts, logs and retry require an
  instance index for a mapped task (none or -1 returns 400); cancel and output take one instance or
  the whole task (none or -1). An out-of-range index returns 400.
- **The CLI uses map indexes for mapped task operations** (D86): Task logs, attempts, output, cancel
  and retry accept `--map-index N`. `runs show` and `dags test` list instances after the task row as
  `fetch[0]`, `fetch[1]`, and so on.
- **Sensors and resources have their own endpoints** (D340): Sensors and resources have endpoints of
  their own. Resources appear inside a run’s detail.
