## Current

### Size and ports

- **Deploy schedr ui by default in the distributed chart** (D37): The distributed chart deploys one
  UI replica and a Service on port 8082. Its default deployment is the release’s webserver; no
  Ingress is created.

### Images

- **A slim image beside the full one** (D383): Besides the full image (every connection type, D212,
  the default), 1.0.0 ships `schedr-slim`: Python and schedr without the database and SSH clients.
- **Images on glibc beside Alpine; Alpine tagged -alpine** (D454): From 1.0.0 each image (`schedr`,
  `schedr-slim`, `schedr-server`) is built twice for x86_64: on glibc from the manylinux wheel,
  `python:3.14.8-slim` (Debian), the plain tag (`1.0.0`, `1.0`), and on Alpine from the musllinux
  wheel, tagged `-alpine` (`1.0.0-alpine`, `1.0-alpine`). The plain tag meant Alpine in 0.1.0. The
  glibc base image takes PostgreSQL 18's client from PostgreSQL's apt source (Debian 13 has 17,
  whose `pg_dump` refuses an 18 server). Not chosen: a suffix for glibc; separate image names;
  Ubuntu; distroless.

### Upgrades and compatibility

- **Upgrade-rule gaps: the clear ones fixed, the others asked** (D439): M4.15's check of the upgrade
  rules against what M2 built fixes the gaps the archived rules (Upgrades and compatibility) settle;
  a gap needing a choice stops the step for the user, with what was done committed.
- **A DAG that no longer parses after a major upgrade is held** (D441): As any file that fails to
  import (D72): every DAG of the file is held, no new runs, manual triggers refused, running runs
  finish. The hold's reason names the schedr version the file failed with and says to fix the file
  or roll back. Not chosen: keeping the older parse in use (the archived design's "last good version
  keeps running").

### Access and authentication

- **A worker's certificate names its role, and with an opt-in its ID; standalone's ports under in-
  memory mTLS** (D520): schedr trusts its nodes: a compromised node is out of scope, and so is
  defending it (the plugin's local link unencrypted, no in-memory database, no plugin as its own OS
  user). The master requires a worker's client certificate to name `[tls] worker_name`, so another
  role's certificate (the webserver's, `schedr ui`'s) can't act as a worker; with `[tls]
  worker_identity = "certificate"` the worker ID must be named too, as the DNS name
  `<id>.<worker_name>` (the ID a lowercase DNS label, never matched through a wildcard) (the chart
  issues one per pod through cert-manager's CSI driver), checked at registration, so one worker
  can't act as another. In mesh mode the chart's AuthorizationPolicy lets only the workers' service
  account reach the master's gRPC port; per-worker identity isn't available there. Every worker
  message about an attempt is taken only from the attempt's worker, and a parse upload only of the
  code the worker reported or a job it was given. Standalone's gRPC port and log endpoint use mTLS
  made in memory at each start (a CA and certificates of 24 h, renewed after 12 h of wall time,
  never on disk); what it creates is private (its data directory 0700, its SQLite file 0600), and an
  existing one or a config or password file others can read is warned of at start. Standalone's REST
  API with auth `none` is every local user's: warned of at start, also on loopback, and documented
  (not: requiring auth unless a flag says, the API on a Unix socket). The cleanup barrier keeps its
  socket file (a 0700 folder), documented. Not chosen: per-worker identity required (it breaks app-
  mode deployments sharing the chart's certificate), a SPIFFE URI (a trust domain to set),
  certificates for the process's life, refusing to start on loose files, the barrier as a socket
  pair, standalone's SQLite in memory.
